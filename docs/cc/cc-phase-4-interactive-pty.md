# Phase 4 — Interactive PTY

## Scope
- Remote terminals via CC: open/write/resize/close mapped to agent PTYs.

## Current implementation note

This phase is still design-only in the current codebase pair (`SuperControlPanel` + `cc-server`):

- the local app already has PTY commands for its own UI
- the CC agent/server protocol does not yet define or handle remote `open_pty`, `write_pty`, `resize_pty`, or `close_pty`
- there is no remote Admin terminal UI or CC-mediated PTY session lifecycle yet

Treat the rest of this document as the target design, not as shipped behavior.

## Phase 4 design decisions

The initial Phase 4 PTY implementation should intentionally choose the simpler ownership model:

- `sessionId` is generated by **cc-server**, not by the agent
- `sessionId` is the canonical external identity used by Admin UI, cc-server, audit records, and agent PTY events
- the agent may keep its own internal/local PTY identifier, but it must map it back to the server-issued `sessionId`
- remote PTY sessions are **single-operator owned** in Phase 4
- only one active operator attachment is allowed for a PTY session in the initial implementation
- reconnect/reattach is allowed only for the same still-open session owned by the same operator
- a different operator attempting to attach to an already-owned PTY should be rejected with a stable busy/unauthorized error rather than silently sharing the session
- collaborative/shared multi-attach terminals are explicitly out of scope for Phase 4

### Why this choice

- simpler audit attribution for input and session ownership
- no concurrent typing / resize conflicts
- easier reconnect and lifecycle reconciliation
- clearer privacy and recording-consent model
- lower implementation risk for the first remote terminal slice

## Transport model

Phase 4 should use a split transport model:

- **agent ↔ cc-server:** reuse the existing `/agent` websocket and CC protocol envelopes
- **Admin UI ↔ cc-server:** use a separate browser-facing PTY transport owned by `cc-server`

### Chosen direction

- cc-server sends `open_pty`, `write_pty`, `resize_pty`, and `close_pty` to the agent over the existing agent websocket
- agent sends `pty-output` and `pty-exit` back to cc-server over that same websocket
- Admin UI does **not** connect directly to the agent
- Admin UI connects only to cc-server for live PTY interaction
- cc-server relays PTY output from agent to the browser-facing Admin PTY stream
- cc-server relays Admin input/resize/close requests into the agent websocket protocol

### Why this split is preferred

- keeps the agent connection model simple and unchanged from the agent's perspective
- avoids exposing agent websocket details directly to browser clients
- lets cc-server enforce auth, RBAC, audit, privacy banner state, and operator ownership centrally
- makes reconnect handling cleaner: browser reconnect is separate from agent reconnect
- keeps room for future Admin transport changes without changing the agent protocol

### Operational implications

- cc-server owns browser-session ↔ PTY-session attachment state
- agent owns actual PTY process/runtime state
- if Admin disconnects briefly, cc-server may allow same-operator reattach to the same live PTY session
- if the agent disconnects, cc-server should mark attached Admin PTY sessions as degraded and reconcile when the agent returns

## Admin-facing PTY transport

The Admin/browser side should use a dedicated websocket transport exposed by `cc-server`.

### Chosen direction

- use **WebSocket** for Admin PTY transport
- do not use SSE for the live terminal stream
- do not split terminal control across SSE + POST in the initial implementation

### Why WebSocket

- PTY interaction is bidirectional and latency-sensitive
- terminal input, resize, and close events fit naturally into a duplex channel
- attach/reconnect state is easier to manage with one persistent browser connection
- server can push lifecycle, replay, warning, and terminal-exit events without extra polling

### Proposed browser transport shape

- endpoint example: `/admin/ws/pty`
- auth: existing Admin browser session auth
- one websocket connection may carry multiple PTY-related messages, but Phase 4 may limit a browser tab to one active PTY attach for simplicity

### Browser → cc-server messages

- `pty_open`
  - `{ deviceId, sessionId, cols, rows, recording? }`
- `pty_attach`
  - `{ deviceId, sessionId }`
- `pty_write`
  - `{ sessionId, data }`
- `pty_resize`
  - `{ sessionId, cols, rows }`
- `pty_close`
  - `{ sessionId, reason? }`

### cc-server → Browser messages

- `pty_opened`
  - `{ sessionId, state }`
- `pty_replay`
  - `{ sessionId, data, truncated? }`
- `pty_output`
  - `{ sessionId, data }`
- `pty_resized`
  - `{ sessionId, cols, rows }`
- `pty_exit`
  - `{ sessionId, exitCode?, reason }`
- `pty_state`
  - `{ sessionId, state, detail? }`
- `pty_error`
  - `{ sessionId?, code, message, retryAfterMs? }`

### Browser transport notes

- browser message names do not need to exactly match agent protocol names, as long as cc-server translates them deterministically
- `cc-server` should preserve stable `sessionId` values across browser and agent transports
- replay should be sent before live output resumes on reattach
- `pty_error` should carry stable codes derived from the PTY error taxonomy where possible

## `pty_open` vs `pty_attach`

Phase 4 should keep **open** and **attach** as separate concepts in the model, even if the first Admin UX combines them into one action.

### Chosen direction

- `pty_open` creates a new remote PTY session
- `pty_attach` attaches the current browser/operator to an already-existing PTY session
- the first Phase 4 Admin UI may perform these together as an implicit open-and-attach flow
- reconnect flows should prefer `pty_attach`, not `pty_open`

### Why keep them distinct

- avoids accidentally creating a new PTY during reconnect
- makes the lifecycle model clearer (`opening` / `open` session existence vs browser attachment state)
- gives room for future attach/reattach UX without redefining protocol semantics
- supports bounded scrollback replay on reattach without pretending it is a brand-new PTY

### Phase 4 practical rule

- "Open terminal" in the Admin UI = `pty_open` followed by immediate `pty_attach`
- browser reconnect to a known live session = `pty_attach`
- attaching to a terminal in a terminal state (`closed`, `expired`, `failed`) must fail rather than create a replacement PTY

## Detach vs close

Detach and close should be treated as different concepts, even if the first Phase 4 transport keeps detach lightweight.

### Chosen direction

- `close_pty` means terminate the remote PTY session itself
- browser detach means the operator/browser is no longer attached, but the PTY may remain alive briefly for reattach
- Phase 4 may avoid a first-class `pty_detach` message and instead treat browser websocket disconnect as an implicit detach

### Phase 4 practical behavior

- explicit terminal close from the Admin UI sends `pty_close`
- closing or losing the browser websocket is treated as detach, not immediate PTY termination
- after detach, `cc-server` may keep the PTY session reattachable for a short grace window
- when the grace window expires, `cc-server` should close or expire the PTY according to the configured idle/disconnect cleanup policy

### Why this split matters

- avoids killing terminals just because a browser tab reloads or a network hop blips
- preserves the same-operator reattach flow
- keeps lifecycle and audit semantics clearer:
  - detach = attachment changed
  - close = PTY lifetime ended by request

## Grace window and cleanup policy

Phase 4 should define conservative defaults so reattach works without leaving abandoned PTYs around too long.

### Recommended defaults

- **reattach grace window:** 30 seconds
- **hard idle timeout for detached PTY sessions:** 5 minutes
- **cleanup check cadence:** at least every 5 seconds

### State behavior

- browser disconnect while PTY is still healthy:
  - session remains `open`
  - marked internally as detached / reattachable
  - same operator may `pty_attach` again within the grace window
- grace window expires with no successful reattach:
  - session becomes eligible for cleanup
  - cc-server should request PTY close or mark it `expired` according to the cleanup path
- detached PTY reaches hard idle timeout:
  - session transitions to `expired`
  - agent/server cleanup must release underlying PTY resources

### Operational rules

- explicit `pty_close` should always win immediately over grace-window retention
- same-operator reconnect during the grace window cancels pending expiry
- different-operator attach during the grace window remains rejected
- if the agent reports PTY exit during the grace window, session transitions to `closed`, not `expired`
- if the agent connection is lost, cc-server should mark the session degraded and reconcile on reconnect before deciding expiration

### Why these defaults

- 30 seconds is long enough for page reloads, brief Wi-Fi hiccups, and browser reconnects
- 5 minutes bounds resource leakage if an operator disappears entirely
- frequent cleanup checks keep expiry predictable without requiring per-session busy loops

## Audit expectations

Remote PTY sessions should produce explicit audit records. Phase 4 should treat PTY access as an operator-visible control action, not just a transport detail.

### Minimum PTY audit events

- `pty_open_requested`
- `pty_open_succeeded`
- `pty_open_failed`
- `pty_attach_succeeded`
- `pty_attach_rejected`
- `pty_detached`
- `pty_close_requested`
- `pty_closed`
- `pty_expired`
- `pty_recording_consent_granted`

### Recommended audit fields

- `ts`
- `deviceId`
- `sessionId`
- `actorType`
- `actorId`
- `eventType`
- `source` (`admin_ui`, `server`, `agent`, `reconciler`)
- `summary`
- `detailsJson` (redacted)

### Audit rules

- same-operator reattach should still produce an audit entry
- attach rejection by another operator must be auditable
- record-enabled sessions must audit the consent event before input is accepted
- PTY expiration/cleanup should be auditable even when no user explicitly clicked close
- audit payloads must never store raw PTY input contents, passwords, tokens, or full replay data

## Protocol
- CC → Agent: `open_pty`, `write_pty`, `resize_pty`, `close_pty`.
- Agent → CC: `pty-output`, `pty-exit` with `{sessionId}`.

## Remote PTY session lifecycle

Remote PTY should use a small explicit lifecycle so agent, server, and Admin UI all reason about the same states:

- `opening`
  - server accepted an `open_pty` request and is waiting for the agent to create the PTY
- `open`
  - PTY exists and can accept input / resize
- `closing`
  - close requested, or terminal exit observed and cleanup is in progress
- `closed`
  - PTY fully terminated; terminal result is known
- `expired`
  - PTY was garbage-collected after idle/disconnect timeout
- `failed`
  - PTY could not be opened or reconciled successfully

### Lifecycle rules

- `open_pty` moves a session from nonexistent → `opening` → `open` or `failed`
- `write_pty` and `resize_pty` are only valid in `open`
- `close_pty` moves `open` → `closing` → `closed`
- agent-observed PTY exit moves `open` → `closing` → `closed`
- idle timeout / disconnect GC moves `open` → `expired`
- terminal states are `closed`, `expired`, and `failed`
- terminal states do not transition back to `open`; a new PTY requires a new `sessionId`

### Reconnect / attach behavior

- Admin reconnect to an `open` PTY should reattach to the same `sessionId`
- reattach may replay bounded scrollback before live output resumes
- reconnect to `closed` / `expired` / `failed` should not silently create a new PTY
- if server and agent disagree, agent PTY state is the source of truth and server reconciles to it
- attach by a different operator to an already-owned live PTY is rejected in Phase 4

## Agent
- PTY multiplex; backpressure to CC on slow consumers.
- Idle timeout + server-side session GC.

## PTY hardening
- Input and encoding
  - UTF-8 only; invalid sequences replaced with U+FFFD.
  - Enable bracketed paste; do not split pasted chunks mid-UTF8 rune.
  - Pass-through mouse reporting (xterm SGR mode) when enabled by the app.
  - Sanitize NUL and disallowed control sequences; drop ESC [ 8 ; ... ; t (window ops), OSC 52 (clipboard) unless explicitly allowed in org policy.
- Windows vs Unix
  - Windows: ConPTY; Unix: `portable-pty`. Normalize resize semantics (cols×rows) and CRLF handling so apps see consistent behavior.
  - Wide-char rendering sanity checks on first attach; warn if detected terminal font width mismatch.
- Rate limits and abuse protection
  - Keystrokes: average 100 cps, burst up to 200 cps (token-bucket). Excess input dropped and `nack { rate_limited: true }` surfaced to UI.
  - Resize: 10/s steady, burst up to 20/s. Additional resizes coalesced (drop intermediate) with last-known applied.
- Scrollback and replay
  - Per-session scrollback cap: 128 KB (org-configurable: 32–512 KB). On attach, replay up to the cap. Truncation is indicated with a header line.
  - Optional server-side recording does not change scrollback size; recording writes are async and bounded by backpressure rules.
- Recording and privacy
  - Recording: off by default; org-configurable retention (default 7 days). Redaction rules applied (see Telemetry Redaction Matrix).
  - Privacy banner is displayed to the operator on record-enabled sessions; operator must acknowledge before input is sent.
- Security and RBAC
  - Enforce per-session ACL checks before open/write/resize/close. Deny emits `nack { status: "unauthorized" }`.
  - Explicit consent required for record-enabled sessions; consent stored in audit with actor, device, session, timestamp.
## CC / Admin UI
- Live terminal component; per-session ACLs.
- Replay last N KB scrollback on attach (agent keeps short buffer).

## Acceptance Criteria
- Keystroke → echo <120 ms P50 over WAN.
- Resize reflects within one frame.
- Session cleanup on disconnect; scrollback replay works and truncates with notice.
- RBAC enforced; recording flag is visible and audited.

## Risks
- Abuse/DoS via spam → rate limits + RBAC.
- Unicode/input edge cases → pass-through with tests.

## SLOs (Phase 4 PTY)
- Keystroke → echo: P50 ≤ 120 ms, P95 ≤ 300 ms (WAN)
- Resize propagation: first paint within 1 frame (≤ 100 ms target)
- Attach to running session: scrollback delivered ≤ 300 ms for 128 KB buffer
- Session cleanup: idle timeout enforced ≤ 5 s after threshold
- Error budget: <0.1% `nack rate_limited` under steady-state typing; bursts may be limited per policy

## Test plan (Phase 4 PTY)

- Keystroke echo latency
  - Simulate 100 keystrokes at 5 Hz and 20 Hz over WAN-like latency (100–200 ms RTT) and assert P50 ≤ 120 ms, P95 ≤ 300 ms echo from `pty-output`.
- Resize behavior
  - Emit rapid `resize_pty` events (10 resizes over 2s). Assert the terminal reflects dimensions within one frame and no garbled output.
- Scrollback replay
  - Produce 200 KB output, detach, reattach. Assert only last 64–128 KB (configured) replays, with truncation notice present.
- Recording flag & privacy banner
  - Start session with recording enabled; assert banner rendered and audit entry created. With recording disabled, banner absent.
- Rate limit/abuse protection
  - Send keystrokes at 200 Hz for 10s; assert `nack rate_limited` and graceful degradation (no agent crash), then recovery after cooldown.
- Cross-platform
  - Windows (ConPTY) vs Unix (portable-pty): verify wide-char rendering, paste, mouse reporting, and consistent resize semantics.
- Security
  - Verify per-session ACL enforcement: unauthorized actor cannot attach; attempt is audited with `unauthorized`.
- Cleanup
  - Idle timeout triggers server-side GC; session is closed and no residual resources leak.
